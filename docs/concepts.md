## Step 01 — مقدمة
> المصدر: *AI Engineering* Ch.1 — الشرح في [`steps/01-introduction/notes/01-chip-huyen-ch1.md`](../steps/01-introduction/notes/01-chip-huyen-ch1.md)

### Language Model
📍 Ch.1 ص 2
- **إيه هو؟** موديل شايل معلومات إحصائية عن اللغة: كلمة معيّنة احتمال تيجي قد إيه في سياق معيّن.
- **مثال:** "أنا بشرب الشاي بـ ___"، الموديل يدّي "سكر" احتمال أعلى من "كيبورد".
- **ليه اتعمل؟** عشان الكمبيوتر يتوقع النص ويولّده. ومن التوقع ده بتطلع الترجمة، والتلخيص، والتصنيف، والكود.
- **المقابل في Laravel:** مفيش مقابل مباشر. أقرب حاجة autocomplete ضخم جداً.
- **إمتى / إمتى لأ:** مناسب لأي حاجة شكلها "نص يتكمّل". ⚠️ الرد **توقّع احتمالي**، مش حقيقة مضمونة.

### Token و Tokenization و Vocabulary
📍 Ch.1 ص 3–4
- **إيه هو؟** الـ **token** هو وحدة النص اللي الموديل بيشتغل بيها (حرف، أو كلمة، أو جزء من كلمة). الـ **tokenization** هي عملية تقطيع النص لـ tokens، والـ **vocabulary** هي كل الـ tokens اللي الموديل يعرفها.
- **مثال:** `cooking` ممكن تبقى `cook` + `ing`. في الإنجليزي، الـ 100 token حوالي 75 كلمة.
- **ليه اتعمل؟** حل وسط: عدده أقل من الكلمات فالموديل أكفأ، ومعناه أكتر من الحروف، وبيتعامل مع الكلمات الجديدة.
- **المقابل في Laravel:** زي segments الـ SMS: وحدة الحساب، والعربي بياخد منها أكتر. وزي `token_get_all()` في PHP، بس tokens الموديل **قطع إحصائية** مش قواعد لغة.
- **إمتى يهمك؟** دايماً. الـ tokens هي **وحدة التكلفة** و**حجم الـ context**. والعربي غالباً بياخد tokens أكتر من الإنجليزي.

### Autoregressive LM و Masked LM
📍 Ch.1 ص 4–5
- **إيه هو؟** الـ **autoregressive** بيتوقع الـ token اللي جاي من اللي قبله بس (GPT وأغلب الـ LLMs). الـ **masked** بيملى فراغ في أي حتة، وبيبص على اللي قبله واللي بعده (BERT).
- **مثال:** autoregressive: "أنا بحب الشاي بـ ___". masked: "أنا بحب ___ بالسكر".
- **ليه اتعمل؟** الـ autoregressive بيقدر **يولّد** token ورا token، والـ masked أحسن في **فهم** النص كله (تصنيف، و embeddings).
- **المقابل في Laravel:** الـ autoregressive زي `while` loop بيلزق token في آخر الـ output، ويبص على كل اللي فات عشان يقرر اللي بعده.
- **إمتى / إمتى لأ:** للتوليد (chat، وكتابة، وكود) الـ autoregressive. والـ masked موجود ورا كتير من الـ embedding models والـ classifiers (Step 07).

### Completion و Generative AI
📍 Ch.1 ص 5–6
- **إيه هو؟** الـ language model **completion machine**: بياخد نص (**prompt**) ويكمّله. ولأن الـ output مفتوح (open-ended) اسمه **generative**.
- **مثال:** `Is this email spam? Email: ... Answer:`، الموديل يكمّل بـ "spam"، فبقى classifier.
- **ليه اتعمل؟** مهام كتير (ترجمة، وتصنيف، وتلخيص) ممكن تتصاغ كـ "كمّل النص".
- **المقابل في Laravel:** Blade template سايب آخره فاضي، والموديل بيملاه.
- **إمتى / إمتى لأ:** الـ completion الخام **مش chat**: ممكن يرد على سؤالك بسؤال. عشان كده بنستخدم موديلات chat/instruct اللي عدّت على post-training.

### Self-supervision (مقابل Supervision)
📍 Ch.1 ص 6–8 · 🚫 تفاصيل التدريب برّه النطاق
- **إيه هو؟** الـ **supervision** هو التدريب على أمثلة عليها labels بشرية (غالية وبطيئة). الـ **self-supervision** هو إن الموديل بيطلّع الـ labels من الداتا نفسها. وده غير الـ **unsupervised**، اللي مفيهوش labels خالص.
- **مثال:** جملة `Laravel is a PHP framework` بتدّيك أمثلة ببلاش: بعد `Laravel` ييجي `is`، وبعد `Laravel is` ييجي `a`...
- **ليه اتعمل؟** عشان يعدّي عنق زجاجة الـ labeling. النص موجود في كل حتة، فالموديلات قدرت تكبر لحد ما بقت LLMs.
- **المقابل في Laravel:** مفيش.
- **إمتى يهمك؟** كفهم بس: الموديل اتعلم من نص الإنترنت، فهو شاطر في اللي شافه كتير، ومايعرفش داتا شركتك ولا الأحداث اللي بعد تدريبه.

### Parameters (Weights)
📍 Ch.1 ص 8
- **إيه هو؟** المتغيّرات اللي جوه الموديل وبتتظبط أثناء التدريب. عددها هو "حجم" الموديل.
- **مثال:** `qwen2.5:3b` يعني حوالي 3 مليار parameter، والملف اللي بينزل (~2GB) هو الـ weights دي.
- **ليه يهمك؟** parameters أكتر غالباً (مش دايماً) = قدرة أكبر، بس RAM أكتر وأبطأ وأغلى.
- **المقابل في Laravel:** مفيش مقابل مباشر. فكّر في ملف الـ weights كـ "build artifact" بيتوزع زي ما الـ package بتتوزع.
- **إمتى / إمتى لأ:** بيفيدك وإنت بتختار موديل local يشتغل على جهازك. ⚠️ الموديلات المقفولة مش بتعلن الرقم، والـ MoE ليها حجم كلي وحجم "شغّال".

### LLM (Large Language Model)
📍 Ch.1 ص 8
- **إيه هو؟** language model كبير، اتدرّب بـ self-supervision على كمية نص ضخمة.
- **مثال:** GPT، و Claude، و Llama، و Qwen.
- **ليه اتعمل؟** لأن الحجم الأكبر مع داتا أكتر جاب قدرات أكتر.
- **المقابل في Laravel:** —
- **ملاحظة:** "large" مش مصطلح علمي، واللي كبير النهارده صغير بكرة.

### Foundation Model
📍 Ch.1 ص 9–10
- **إيه هو؟** موديل عام كبير (LLM أو multimodal) بتبني فوقه تطبيقات كتير مختلفة.
- **مثال:** نفس الموديل يترجم، ويلخّص، ويصنّف، ويكتب كود، ويفهم صور.
- **ليه اتعمل؟** بدل موديل لكل مهمة (task-specific)، موديل واحد general-purpose. ده بيقلّل التكلفة والوقت لحد ما المنتج ينزل السوق.
- **المقابل في Laravel:** Laravel نفسه، أساس بتبني فوقه وتظبطه بدل ما تكتب كل حاجة من الصفر.
- **إمتى / إمتى لأ:** ده الافتراضي بتاعك. لكن الموديل المتخصص الصغير ممكن يبقى أسرع وأرخص لمهمة واحدة بحجم كبير.

### Multimodal Model (LMM)
📍 Ch.1 ص 9
- **إيه هو؟** موديل بيتعامل مع أكتر من نوع داتا (نص، وصور، وصوت، وفيديو). ولو generative اسمه **LMM**.
- **مثال:** تبعتله صورة فاتورة وتسأله "الإجمالي كام؟".
- **ليه اتعمل؟** العالم مش نص بس، وأبحاث الـ AI كانت متقسّمة حسب نوع الداتا (NLP، و vision، و audio).
- **المقابل في Laravel:** —
- **إمتى / إمتى لأ:** لما الداتا صور أو PDFs أو صوت (Step 13). وفيه موديلات local بتفهم صور في Ollama.

### Embedding
📍 Ch.1 ص 10 · الشرح الكامل في Step 07
- **إيه هو؟** vector (لستة أرقام) بيمثّل "معنى" نص أو صورة، والحاجات اللي معناها قريب بيبقى الـ vectors بتاعتها قريبة.
- **مثال:** "إجازة سنوية" و "أيام الـ vacation" ليهم embeddings قريبة، مع إن الكلمات مختلفة.
- **ليه اتعمل؟** عشان تبحث وتقارن **بالمعنى** مش بالكلمات.
- **المقابل في Laravel:** البحث بـ `LIKE '%...%'` بيدوّر على الكلمة. الـ embeddings بتدوّر على المعنى (هنحطها في PostgreSQL بـ pgvector في Step 08).
- **إمتى:** البحث الذكي والـ RAG. (CLIP مثال على embedding model للصور والنص، ومش generative.)

### Model as a Service
📍 Ch.1 ص 1، ص 14
- **إيه هو؟** شركات قليلة بتدرّب الموديلات، وبتقدّمها للباقي كـ **API**.
- **مثال:** `POST` بالرسايل لـ Anthropic API، وترجعلك الرد.
- **ليه اتعمل؟** تدريب الموديلات غالي جداً، فبدل ما كل واحد يبني موديله، الكل بيأجّر.
- **المقابل في Laravel:** زي Stripe أو SES: مش بتبني payment gateway أو mail server، بتنادي API.
- **إمتى / إمتى لأ:** الافتراضي للجودة العالية. ⚠️ داتاك بتخرج برّه جهازك، فللداتا الحساسة فكّر في local بـ Ollama (Step 03).

### AI Engineering (مقابل ML Engineering)
📍 Ch.1 ص 12، ص 39–40
- **إيه هو؟** بناء تطبيقات **فوق foundation models جاهزة**. الـ ML engineering التقليدي بيـ**طوّر** موديلات، والـ AI engineering بيـ**كيّفها ويقيّمها**.
- **الـ 3 فروق:** (1) بتستخدم موديل حد تاني بدل ما تدرّب، (2) موديلات أكبر فيها latency وتكلفة أعلى، (3) outputs مفتوحة فالـ evaluation أصعب.
- **ليه ظهر دلوقتي؟** قدرات عامة + استثمارات + حاجز دخول قليل.
- **المقابل في Laravel:** الفرق بين اللي بيطوّر PHP engine واللي بيبني تطبيقات بـ Laravel.
- **ده نطاق الريبو ده.**

### Model Adaptation: Prompt Engineering و RAG و Finetuning
📍 Ch.1 ص 11، ص 40 · Steps 05 و 09
- **إيه هو؟** طرق تخلّي الموديل العام يعمل اللي إنت عايزه. **Prompt-based** (من غير ما تغيّر الـ weights): **prompt engineering** (تعليمات وأمثلة) و **RAG** (تجيب داتا مناسبة وتحطها في الـ context). و **finetuning**: تكمّل تدريب الموديل فالـ weights بتتغيّر.
- **مثال:** أوصاف منتجات بصوت البراند: prompt فيه أمثلة ← RAG على reviews العملاء ← finetuning على أوصاف ممتازة.
- **ليه اتعمل؟** الموديل الجاهز "كويس" بس مش مظبوط على حالتك.
- **المقابل في Laravel:** prompt = تنادي package بـ config و arguments. RAG = الـ controller بيجيب داتا ويبعتها للـ view. finetuning = fork للـ package وتعدّل الـ source.
- **إمتى:** ابدأ دايماً بالـ prompt، بعدين RAG لو محتاج معلومات الموديل مايعرفهاش، والـ finetuning آخر حل (أعقد ومحتاج داتا، بس ممكن يحسّن الجودة والتكلفة والـ latency). ⚠️ لو حطيت داتا في الـ prompt فده **مش** training ولا finetuning.

### Pre-training و Post-training و Finetuning
📍 Ch.1 ص 41–42 · 🚫 التنفيذ برّه النطاق
- **إيه هو؟** **pre-training** = تدريب من الصفر (أغلى مرحلة بمراحل). **post-training** = تدريب بعدها بيعمله صاحب الموديل (مثلاً عشان يتبع التعليمات ويبقى chat). **finetuning** = نفس الفكرة، بس بيعمله مطوّر التطبيق على داتاه.
- **مثال:** الـ base model اللي بيكمّل نص ← (post-training) ← chat model بيرد عليك ← (finetuning من شركة) ← موديل متخصص في دعم عملائها.
- **ليه يهمك؟** عشان تفهم الموديل اللي بتستخدمه جه منين، ومتقولش "درّبت الموديل" وإنت كتبت prompt.
- **المقابل في Laravel:** الفرق بين إنك تبعت arguments وقت التشغيل، وإنك تعدّل الكود وتعمل deploy.
- **ملاحظة:** الـ quantization بتغيّر الـ weights بس **مش** training.

### Inference و Inference Optimization و Quantization
📍 Ch.1 ص 34، ص 43–44
- **إيه هو؟** الـ **inference** هو حساب الـ output من الـ input (يعني كل مرة بتنادي الموديل). والـ **inference optimization** هو إنك تخلّيه أسرع وأرخص. والـ **quantization** إنك تقلّل دقة الأرقام في الـ weights فالموديل يصغر ويسرع.
- **مثال:** لو الـ token بياخد 10ms، يبقى رد من 100 token بياخد ثانية. والموديلات اللي في Ollama غالباً quantized (مثلاً 4-bit)، فموديل 3B حجمه حوالي 2GB.
- **ليه يهمك؟** الموديلات autoregressive (token ورا token)، فبطيئة مقارنة بـ API عادي بيرد في 100ms.
- **المقابل في Laravel:** الـ quantization زي ضغط صورة JPEG بجودة 80%.
- **إمتى:** كـ AI Engineer، إنت **بتختار** (موديل أصغر أو quantized) و**بتصمم** حوالين البطء (streaming، و queues، و caching). تنفيذ التكنيكات نفسها 🚫 برّه النطاق.

### Human-in-the-loop و Crawl-Walk-Run
📍 Ch.1 ص 31
- **إيه هو؟** إن فيه إنسان مشارك في قرارات الـ AI. و **Crawl-Walk-Run** (من Microsoft) طريقة تزوّد بيها الأوتوماتيك بالتدريج: الإنسان إجباري ← الـ AI يتعامل مع الموظفين ← الـ AI يتعامل مع العملاء مباشرة.
- **مثال:** الـ AI يقترح ردود على موظف خدمة العملاء. ولو الموظفين بيقبلوا حوالي 95% من الاقتراحات زي ما هي في الطلبات البسيطة، تسيبه يرد عليها لوحده.
- **ليه اتعمل؟** الـ AI بيغلط، والثقة لازم تتبني بأرقام.
- **المقابل في Laravel:** PR review قبل الـ merge، وبعدين auto-merge للتغييرات الآمنة. أو feature flag (Pennant) بيتفتح للفريق الأول.
- **إمتى:** دايماً في البداية، وبالذات لو الـ AI **critical** أو هيكلّم عملاء أو هياخد actions.

### Usefulness Threshold و TTFT و TPOT
📍 Ch.1 ص 32–33
- **إيه هو؟** **usefulness threshold** = لازم المنتج يبقى كويس لدرجة إيه عشان يبقى مفيد، ويتقاس بالـ quality والـ latency والـ cost وغيرهم. و **TTFT** (time to first token) = الوقت لحد أول token. و **TPOT** (time per output token) = الوقت بين كل token والتاني.
- **مثال:** chatbot هدفه يحل 60% من الـ tickets، و TTFT أقل من ثانيتين، وتكلفة الرد أقل من X.
- **ليه اتعمل؟** عشان المنتج مايوصلش للعملاء قبل ما يجهز، وعشان يبقى عندك رقم تحكم بيه.
- **المقابل في Laravel:** TTFT زي TTFB في الويب. والـ usefulness threshold زي الـ acceptance criteria والـ SLA.
- **إمتى:** قبل ما تبدأ أي AI feature. والـ latency المقبولة **نسبية للبديل الحالي** (لو البني آدم بيرد في ساعة، ثواني تبقى ممتازة).

### AI Engineering Stack (3 طبقات)
📍 Ch.1 ص 37–39
- **إيه هو؟** (1) **Application development**: prompts، و context، و evaluation، و interface. (2) **Model development**: training و finetuning، و dataset engineering، و inference optimization. (3) **Infrastructure**: serving، و compute، و data، و monitoring.
- **ليه يهمك؟** بيحدد شغلك فين: الـ AI Engineer معظمه في الطبقة 1، وبيبدأ من فوق وينزل حسب الحاجة.
- **المقابل في Laravel:** كود تطبيقك ← تطوير PHP engine نفسه ← السيرفرات والـ monitoring (Forge، و Nginx، و Sentry).

### Evaluation (open-ended مقابل close-ended)
📍 Ch.1 ص 44–45 · Step 14
- **إيه هو؟** قياس جودة نظام الـ AI عشان تختار موديل، وتقيس تقدّمك، وتعرف جاهز للـ deployment ولا لأ، وتكتشف المشاكل في الـ production. الـ **close-ended** ليه إجابات محددة (spam ولا لأ)، والـ **open-ended** ليه ردود صح كتير (chatbot).
- **مثال:** قصة Gemini و MMLU: نفس الموديل رقمه اتغيّر جامد حسب طريقة الـ prompting، فالمقارنة ماكانتش عادلة.
- **ليه أصعب؟** الـ outputs مفتوحة، والقدرات واسعة، والتكنيكات كتير.
- **المقابل في Laravel:** PHPUnit `assertEquals` بينفع مع الـ functions الـ deterministic، ومبينفعش مع رد chatbot. الـ **evals هي الـ test suite بتاعة تطبيقات الـ AI**.
- **إمتى:** دايماً، وبالذات قبل ما تبدّل موديل أو prompt.

### Agent
📍 Ch.1 ص 28 · Steps 10–12
- **إيه هو؟** AI بيقدر **يخطط** و**يستخدم tools** (بحث، و APIs، و database...) عشان يخلّص مهمة.
- **مثال:** "احجزلي مطعم": يبحث، ويتصل، ويضيف الميعاد للكاليندر.
- **ليه اتعمل؟** مهام كتير محتاجة تتعامل مع العالم، مش بس تكتب نص.
- **المقابل في Laravel:** controller بيقرر لوحده ينادي أنهي service class وبأنهي arguments، بس قراره **مش deterministic**.
- **إمتى / إمتى لأ:** لما المهمة متعددة الخطوات ومحتاجة tools. ⚠️ خطير من غير حماية وحدود (Step 06).

### Defensibility و Data Flywheel
📍 Ch.1 ص 31–32
- **إيه هو؟** **defensibility** = إيه اللي يحمي منتجك من المنافسين (**moat**). والمزايا التلاتة: technology، و distribution، و data. و **data flywheel** = دايرة: استخدام ← داتا ← منتج أحسن ← استخدام أكتر.
- **مثال:** تطبيق "wrapper" فوق موديل ممكن يتبلع لو الموديل نفسه بقى يعمل نفس الحاجة، أو لو Google ضافتها كـ feature.
- **ليه يهمك؟** عشان تقيّم فكرة الـ AI app قبل ما تبنيها (Task 6).
- **المقابل في Laravel:** —
- **إمتى:** لما بتبيع تطبيق AI كمنتج لوحده. أقل أهمية في الـ features الداخلية.

## Step 01 — مقدمة (المصدر 2)
> المصدر: Karpathy — *Intro to Large Language Models* — الشرح في [`steps/01-introduction/notes/02-karpathy-intro-to-llms.md`](../steps/01-introduction/notes/02-karpathy-intro-to-llms.md)

### Open Weights مقابل Closed (Proprietary) Models
📍 Karpathy 00:22، 23:37
- **إيه هو؟** الـ **open weights** يعني ملف الـ parameters متاح، تنزّله وتشغّله عندك (Llama، و Qwen، و DeepSeek...). الـ **closed** يعني الموديل عند الشركة، وإنت بتوصله من API أو web interface بس (GPT، و Claude، و Gemini).
- **مثال:** `ollama pull qwen2.5:3b` بينزّل الـ weights على جهازك. Claude بتكلّمه بـ API.
- **ليه يفرق؟** الـ closed غالباً أقوى وأسهل. الـ open **تتحكم فيه**، وتعمل له fine-tune، **وداتاك مابتخرجش برّه**.
- **المقابل في Laravel:** SaaS مقفول (Algolia) مقابل أداة open source تشغّلها عندك (Meilisearch).
- **إمتى / إمتى لأ:** الداتا الحساسة، أو offline، أو التكلفة الثابتة، يبقى open/local. أعلى جودة وأقل مجهود تشغيل، يبقى closed. (المقارنة الكاملة في Step 03.)

### Base Model مقابل Assistant (Instruct) Model
📍 Karpathy 14:14، 20:18
- **إيه هو؟** الـ **base model** طالع من الـ pre-training بس، بيكمّل نص كأنه "مستند إنترنت". الـ **assistant/instruct model** عدّى كمان على الـ fine-tuning، فبيرد على الأسئلة كـ assistant.
- **مثال:** تسأل الـ base "إزاي أعمل كذا؟"، ممكن يكمّل بأسئلة تانية. الـ assistant يجاوبك.
- **ليه الاتنين موجودين؟** الـ base أساس تعمل عليه fine-tuning بتاعك (الجزء الغالي اتعمل). الـ assistant جاهز للاستخدام.
- **المقابل في Laravel:** —
- **إمتى:** كـ AI Engineer غالباً عايز **instruct/chat**. وعلى Ollama الاسم العادي للموديل غالباً هو النسخة دي.

### Labeling Instructions و Alignment
📍 Karpathy 14:14–17:52، 22:22
- **إيه هو؟** الـ **labeling instructions** مستند (ممكن مئات الصفحات) الشركة بتكتبه وتحدد فيه الـ assistant يرد إزاي (مثلاً helpful, truthful, harmless)، والـ labelers بيكتبوا ردود مثالية على أساسه. الـ **alignment** هو النتيجة: الموديل **سلوكه وأسلوبه** بقوا زي ما الشركة عايزة.
- **مثال:** أسلوب Claude، وإمتى يرفض، وإزاي ينسّق الرد، كل ده جاي من المرحلة دي.
- **ليه يهمك؟** سلوك الموديل **اختيار بشري**، مش طبيعة فيه. وكل provider اختار حاجة مختلفة، فالموديلات بتتصرف مختلف مع نفس الـ prompt.
- **المقابل في Laravel:** زي style guide أو coding standards للفريق: بتحدد "الشكل الصح" مش "المعرفة".

### RLHF (Reinforcement Learning from Human Feedback)
📍 Karpathy 21:05 · 🚫 التنفيذ برّه النطاق
- **إيه هو؟** مرحلة تدريب بتستخدم **مقارنات**: الإنسان يختار الرد الأحسن بين ردود الموديل، والمقارنات دي بتحسّن الموديل.
- **مثال:** أسهل تختار أحسن haiku من 3 من إنك تكتب واحد بنفسك.
- **ليه اتعمل؟** المقارنة أسهل وأرخص من كتابة الرد المثالي.
- **المقابل في Laravel:** زي الـ code review: أسهل تقول "الـ PR ده أحسن" من إنك تكتب الـ PR المثالي.
- **ملاحظة:** النهارده فيه كمان RL على مهام ليها إجابة يتأكد منها أوتوماتيك (رياضة، وكود)، وده اللي طلّع الـ reasoning models.

### Hallucination
📍 Karpathy 09:00–11:23 · Ch.1 ص 5 (probabilistic)
- **إيه هو؟** الموديل **بيألّف معلومة** شكلها مقنع بس مش صح، ومن غير ما يقولك إنه مش متأكد.
- **مثال:** رقم ISBN لكتاب مش موجود، أو مرجع لورقة بحثية متألّفة.
- **ليه بيحصل؟** الموديل بيطلّع الكلمة **الأكتر احتمالاً** مش **الصح**، والتدريب ضغط **lossy** ضاعت فيه تفاصيل، فبيملى الفراغ بحاجة "شكلها" صح.
- **المقابل في Laravel:** مفيش. أقرب حاجة طالب بيكتب أي إجابة عشان مايسيبش الورقة فاضية.
- **إزاي تتعامل معاه:** متعتمدش على الموديل كمصدر للحقايق. ادّيله المصدر في الـ context (Task 5، و RAG)، واطلب منه يقول "مش عارف"، واختبر بالـ evals. والموديلات الصغيرة (local) بتألّف أكتر.

### Knowledge Cutoff
📍 Karpathy 04:00 (التدريب بيحصل كل فترة)
- **إيه هو؟** تاريخ آخر داتا الموديل اتدرّب عليها. **أي حاجة بعده مايعرفهاش.**
- **مثال:** تسأله عن حدث حصل الشهر اللي فات، فيقولك مايعرفش، أو **يألّف**.
- **ليه موجود؟** الـ pre-training غالي جداً، فبيحصل كل كام شهر بس.
- **المقابل في Laravel:** زي cache اتعمل في تاريخ معيّن ومبيتحدّثش.
- **الحل:** tools (بحث في الإنترنت) أو RAG على داتا محدّثة.

### Reversal Curse
📍 Karpathy 12:44
- **إيه هو؟** الموديل يعرف "A هو أم B"، ومايعرفش يجاوب "مين ابن A؟".
- **مثال:** "مين أم Tom Cruise؟" يجاوب صح. "مين ابن Mary Lee Pfeiffer؟" ممكن مايعرفش.
- **ليه يهمك؟** دليل إن معرفة الموديل **مش database** تقدر تستعلم عنها من أي اتجاه، وإن الصياغة بتفرق.
- **المقابل في Laravel:** عكس الـ Eloquent relations، اللي بتقدر تمشي فيها في الاتجاهين (`$user->mother` و `$mother->children`).

### Scaling Laws
📍 Karpathy 25:43 · 🚫 المعادلات برّه النطاق
- **إيه هو؟** أداء الموديل **متوقع** من متغيّرين: **N** (عدد الـ parameters) و **D** (كمية الداتا). أكبر + داتا أكتر = أحسن، بثقة.
- **ليه يهمك؟** ده سبب إن الموديلات بتتحسّن كل كام شهر، وسبب الاستثمارات الضخمة. فتطبيقك لازم **يسهّل تبديل الموديل**.
- **المقابل في Laravel:** —
- **ملاحظة:** من أواخر 2024 التحسّن بييجي كمان من **وقت التفكير** (test-time compute) و RL، مش من تكبير الـ pre-training بس.

### Tool Use
📍 Karpathy 27:43–33:32 · Steps 10–12
- **إيه هو؟** الموديل بيطلب يستخدم tool (بحث، أو calculator، أو كود...)، والبرنامج بينفّذ ويرجّعله النتيجة، والموديل يكمّل.
- **مثال:** بدل ما يحسب في "دماغه" ويغلط، بيطلب calculator.
- **ليه اتعمل؟** الموديل وحش في الحساب، والمعلومات الجديدة، والـ actions الحقيقية. الـ tools بتسد النقص ده.
- **المقابل في Laravel:** الموديل بيرجّع `{"tool": "...", "args": {...}}`، والكود بتاعك يعمل `match` وينادي الـ service. **إنت اللي بتنفّذ، مش الموديل.**
- **إمتى / إمتى لأ:** لما المهمة محتاجة داتا حقيقية أو حساب أو action. ⚠️ كل tool = صلاحية، فادّي أقل صلاحيات ممكنة (prompt injection).

### Reasoning Models (System 1 / System 2)
📍 Karpathy 35:00–38:02
- **إيه هو؟** **System 1** = تفكير سريع غريزي (زي الـ LLMs العادية: كل token نفس الوقت). **System 2** = تفكير بطيء منطقي. والـ **reasoning models** (من أواخر 2024) بتولّد "tokens تفكير" قبل الإجابة، فبتحوّل **الوقت لدقة**.
- **مثال:** مسألة رياضة معقدة: الموديل العادي يجاوب على طول وممكن يغلط، والـ reasoning model يفكر ويراجع ويصلّح، وبعدين يجاوب.
- **المقابل في Laravel:** `Cache::get()` سريع، مقابل job بيحسب النتيجة فعلاً (أبطأ وأدق).
- **إمتى / إمتى لأ:** المسائل المعقدة، والكود، والتخطيط. ⚠️ **مش** للمهام البسيطة: tokens أكتر (تكلفة) و latency أعلى.

### Context Window
📍 Karpathy 43:45 · هنرجعله في Step 02
- **إيه هو؟** أقصى عدد tokens الموديل يقدر يشوفه في request واحد (الـ input والـ output مع بعض). ده الـ "RAM" بتاع الموديل.
- **مثال:** لو المحادثة + المستندات أكبر من الـ context window، مش هتساع، ولازم تشيل أو تلخّص.
- **ليه يهمك؟** الموديل **مايعرفش غير اللي في الـ context** + اللي في الـ weights. وكل token في الـ context بتدفع تمنه.
- **المقابل في Laravel:** زي `memory_limit` في `php.ini`، أو أقصى حجم للـ request.
- **إمتى:** دايماً. حط اللي محتاجه بس. والموديلات الـ local الـ context بتاعها أصغر وبيستهلك RAM.

### Stateless LLM (والـ chat history)
📍 Karpathy 43:45 (الـ context هو الذاكرة الوحيدة) · Task 3
- **إيه هو؟** الموديل **مابيفتكرش حاجة بين الـ requests**. كل request منفصل. الـ "ذاكرة" هي إنك **تبعت المحادثة كلها كل مرة**.
- **مثال:** قلتله "اسمي كريم"، وفي request تاني من غير الرسالة دي سألته "اسمي إيه؟"، مش هيعرف.
- **ليه كده؟** الموديل دالة: input ← output. مفيش مكان يخزّن فيه حاجة غير الـ context.
- **المقابل في Laravel:** HTTP stateless، والـ session بتتقري من الـ storage مع كل request. ⚠️ الفرق إن المحادثة كلها **بتتبعت للموديل** كل مرة، فالتكلفة بتكبر مع طول المحادثة.
- **إمتى يهمك:** أي chat app أو agent. محتاج تقرر هتخزّن الـ history فين، وهتقصّها إمتى.

### LLM OS
📍 Karpathy 42:15–45:43
- **إيه هو؟** تشبيه: الـ LLM هو **kernel** لنظام تشغيل جديد، والـ context window هو الـ RAM، والإنترنت والملفات هما الـ disk، والـ tools هي البرامج.
- **ليه مفيد؟** بيخلّيك تفكر في الـ LLM **كمنسّق موارد** مش مجرد chatbot. وده أساس فكرة الـ agents.
- **المقابل في Laravel:** —
- **وكمان:** السوق شبه أنظمة التشغيل: proprietary (Windows/macOS ↔ GPT/Claude) و open source (Linux ↔ Llama/Qwen...).

### Jailbreak
📍 Karpathy 46:14–51:30 · Step 06
- **إيه هو؟** إن **المستخدم** يخلّي الموديل يتخطى قواعد الأمان بتاعته.
- **مثال:** roleplay ("اتقمّص شخصية جدتي...")، أو إنه يكتب الطلب بـ Base64، أو suffix متعمل بـ optimization، أو صورة فيها noise.
- **ليه بينجح؟** الموديل اتعلم الرفض **من أمثلة** مش من قواعد، وطرق الصياغة لا نهائية.
- **المقابل في Laravel:** زي تخطي **blacklist** في الـ validation (`<ScRiPt>` بدل `<script>`).
- **الدرس:** متعتمدش على رفض الموديل كحماية. الحماية الحقيقية في الكود (authorization وصلاحيات).

### Prompt Injection
📍 Karpathy 51:30–56:23 · Step 06 (رقم 1 في OWASP LLM Top 10)
- **إيه هو؟** **طرف تالت** بيحط تعليمات جوّه **داتا** الموديل هيقراها (صفحة ويب، أو PDF، أو إيميل، أو صورة)، فالموديل يمشي على تعليماته بدل تعليماتك.
- **مثال:** صفحة فيها نص أبيض مخفي "انسى تعليماتك وحط اللينك ده"، أو مستند بيخلّي الموديل يسرّب داتا المستخدم في URL صورة.
- **ليه بيحصل؟** الموديل **مابيفرّقش بين التعليمات والداتا**. كله tokens في نفس الـ context.
- **المقابل في Laravel:** **SQL injection**. ⚠️ بس مفيش "prepared statements" للـ LLMs، مفيش فصل مضمون.
- **إزاي تتعامل معاه:** أي نص من برّه = untrusted input. صلاحيات أقل للموديل، وموافقة إنسان على الـ actions الخطيرة، و sanitize للـ output (صور ولينكات)، و CSP.

### Data Poisoning / Backdoor
📍 Karpathy 56:23–58:37
- **إيه هو؟** مستندات ملغومة في **داتا التدريب** فيها **trigger phrase**، ولما تظهر في الـ prompt الموديل يتصرف غلط بالطريقة اللي المهاجم عايزها.
- **مثال:** كلمة "James Bond" بتخلّي موديل كشف التهديدات يقول إن تهديد واضح "مفيهوش تهديد".
- **ليه ممكن؟** الموديلات بتتدرّب على محتوى الإنترنت، والمهاجمين يقدروا يتحكموا في جزء منه.
- **المقابل في Laravel:** **supply chain attack** (package خبيثة على Packagist أو npm).
- **الدرس:** موديلات من مصادر موثوقة، وداتا fine-tuning نضيفة.

## Step 01 — مقدمة (المصدر 3)
> المصدر: swyx — *The Rise of the AI Engineer* — الشرح في [`steps/01-introduction/notes/03-swyx-rise-of-the-ai-engineer.md`](../steps/01-introduction/notes/03-swyx-rise-of-the-ai-engineer.md)

### Shift Right و API Line
📍 swyx ص 1، ص 4
- **إيه هو؟** الـ **API line** هو الخط اللي الموديلات بتتقدّم عنده كـ API. شماله الناس اللي بتبني الموديلات (باحثين، و ML engineers)، ويمينه الناس اللي بتستخدمها في منتجات (AI Engineers، و full-stack). والـ **shift right** يعني إن الشغل والفرص بتتحرك ناحية اليمين.
- **مثال:** مهمة كانت محتاجة فريق research و5 سنين في 2013، بقت محتاجة API docs وبعد الضهر في 2023.
- **ليه حصل؟** الموديلات بقت جاهزة ومتاحة (API أو open weights)، والتدريب بقى لعبة الكبار (GPUs غالية ونادرة).
- **المقابل في Laravel:** زي ما الـ payments اتنقلت من "خبراء تكامل مع البنوك" لأي developer بيستخدم Stripe API.
- **إمتى يهمك:** عشان تعرف إنت واقف فين: **يمين الـ API line**.

### In-context Learning (Few-shot / Zero-shot)
📍 swyx ص 4 · Step 05
- **إيه هو؟** الموديل بيعمل مهمة جديدة بس من اللي في الـ prompt، **من غير ما الـ weights تتغيّر**. **Few-shot** = بأمثلة قليلة في الـ prompt. **Zero-shot** = من غير أمثلة، بالشرح بس.
- **مثال:** تدّيله مثالين لتصنيف آراء العملاء (إيجابي/سلبي)، ويصنّف التالت صح.
- **ليه مهم؟** ده اللي خلّى أي software engineer يقدر "يعلّم" الموديل مهمة في دقايق من غير داتا تدريب.
- **المقابل في Laravel:** زي موظف جديد شاطر، ورّيه مثالين من الشغل ويفهم. ⚠️ بس "بينسى" أول ما تشيل الأمثلة من الـ prompt.
- **إمتى / إمتى لأ:** أول حاجة تجرّبها في أي مهمة. لو محتاج أمثلة كتير جداً أو أداء ثابت على حجم كبير، فكّر في حلول تانية (Step 09).

### "Fire, Ready, Aim" (Product-first)
📍 swyx ص 4–5 · Ch.1 Figure 1-16
- **إيه هو؟** بدل ML التقليدي (**Data ← Model ← Product**)، تبني المنتج الأول بموديل جاهز و prompt، ولو الفكرة نجحت تستثمر في الداتا والموديل (**Product ← Data ← Model**).
- **مثال:** feature تلخيص tickets: prototype بـ API call في يوم، وتقيس هل مفيدة، وبعدين تحسّنها بـ RAG أو موديل أرخص.
- **ليه اتعمل؟** بيخليك تختبر أفكار AI أسرع وأرخص بكتير.
- **المقابل في Laravel:** **Agile مقابل Waterfall**: MVP بسرعة، وتتعلم، وتكرر.
- **إمتى / إمتى لأ:** دايماً في البداية. ⚠️ بس مش معناه تنزّل الـ demo للعملاء. الـ last mile (Ch.1 ص 33) لسه محتاج evaluation وشغل.

### Software 1.0 / 2.0 / 3.0
📍 swyx ص 5–7 (من مقالات Karpathy)
- **إيه هو؟** **1.0** = كود مكتوب بإيد (deterministic). **2.0** = neural networks اتعلمت الـ logic من الداتا. **3.0** = البرنامج هو **prompt بلغة عادية** لـ LLM.
- **مثال:** 1.0: `if ($total > 1000)`. 2.0: موديل fraud اتدرّب على معاملات. 3.0: "صنّف الإيميل ده".
- **ليه مهم؟** بيوضّح إن الـ prompts بقت "كود" ليها نفس المشاكل (versioning، و testing، و security)، بس **probabilistic**.
- **المقابل في Laravel:** الـ prompt زي template أو config بيتحكم في السلوك. عامله كـ **كود**: خليه في ملف، وفي git، وعليه tests (evals).
- **ملاحظة:** التلاتة **بيشتغلوا مع بعض**. التطبيق الحقيقي فيه كود 1.0 كتير حوالين الـ 3.0.

### Code Core مقابل LLM Core
📍 swyx ص 6–7 · Step 11 (workflows vs agents)
- **إيه هو؟** **Code Core**: الكود ماسك الـ flow، والـ LLM بيتنادى في خطوات محددة. **LLM Core**: الـ LLM هو اللي بيقرر الخطوات والـ tools (agents).
- **مثال:** Code Core: controller بيعمل validate، والموديل يصنّف، والكود يعمل `match` ويبعت Job. LLM Core: الموديل يقرر لوحده يبحث، ولا يرد، ولا يفتح ticket.
- **ليه يفرق؟** الـ Code Core أسهل في الاختبار، وأرخص، وأأمن. والـ LLM Core أمرن، بس أصعب وأخطر (prompt injection، والصلاحيات).
- **المقابل في Laravel:** Code Core = service خارجي بتناديه جوّه flow إنت كاتبه. LLM Core = controller بيقرر ينادي إيه، بس قراره مش deterministic.
- **إمتى:** **ابدأ بـ Code Core**، وادّي الموديل تحكم أكتر لما المهمة تحتاج ده فعلاً.
