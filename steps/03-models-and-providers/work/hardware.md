> **الجهاز:** الـ **desktop الشخصي** (مش لاب الشركة). اتسجّل يوم 2026-11-27 من **Task Manager ← Performance** (Step 03، Task 0).
> ⚠️ لو شغّلت تجارب Tasks 3 و 4 و 6 على لاب الشركة، الأرقام (الـ load time، و tokens/s، والـ PROCESSOR) **مش هتتقارن** بأرقام الجهاز ده. سجّل كل نتيجة اتعملت على أنهي جهاز.
> الـ hardware ده **hard attribute** لأي موديل local: بيحدد أكبر موديل ينفع يشتغل وسرعته قد إيه (شرح الكتاب Ch.4 جزء 5.1، وشرح Ollama جزء 6).

## يعني إيه للموديلات الـ local؟

### 1. الموديل بيشتغل على الـ CPU والـ RAM
- Ollama بيشتغل أسرع على GPU **متوافق**: NVIDIA (CUDA)، أو AMD (ROCm)، أو Apple (Metal)، أو كروت تانية عن طريق Vulkan (شرح Ollama جزء 6). وجهازي مفيهوش NVIDIA ولا AMD.
- الـ UHD 770 **مالوش memory خاصة بيه**. الـ *Shared GPU memory* اللي بتظهر في Task Manager هي **جزء من نفس الـ 32 GB RAM**. فحتى لو Ollama استخدمه عن طريق Vulkan، **مش هكسب memory زيادة**، والموديل هيقرا من نفس الـ RAM بنفس السرعة تقريباً.
- عشان كده لما `qwen2.5:3b` اتحمّل على جهاز التحضير طلع `size_vram = 0`، يعني **100% CPU** (شرح Ollama جزء 4.3). والمتوقع هنا نفس الحاجة.
- ✅ **الحقيقة بتيجي من القياس مش من الكلام ده:** بعد أول request، `ollama ps` ← عمود **PROCESSOR** (و `size_vram` في `/api/ps`). هسجّلها في Task 3 و 4.
- ✅ **اتقاس في Task 3 (2026-11-27):** `ollama ps` ← **`100% CPU`**، و `size_vram = 0`، و 2.16 GB في الـ memory، و context 4,096. والتوليد **~28 tok/s**، وتحميل الموديل **~1.6 ث** (التفاصيل في `observations.md`).

### 2. الـ default context هيبقى 4K
- Ollama بيختار الـ default context حسب الـ VRAM. **أقل من 24 GiB يبقى 4K** (شرح Ollama جزء 5). وأنا عندي 0 VRAM، فالـ default هيبقى **4096**، وده نفس اللي اتشاف على جهاز التحضير.
- لو عايز context أكبر، لازم أبعت `num_ctx` صريح. والتمن: **KV cache أكبر في الـ RAM**. ده بالظبط اللي هقيسه في Task 4.

### 3. أكبر موديل ينفع يشتغل: الـ RAM هي الحد
- الـ memory اللي الموديل محتاجها تقريباً = **حجم ملف الموديل** (الـ weights بعد الـ quantization) **+ الـ KV cache** (بيكبر مع `num_ctx`) **+ overhead**.
- من الـ 32 GB، Windows و PyCharm والـ browser بياخدوا جزء كبير، فالمتاح عملياً للموديل حوالي **15–20 GB**. (الرقم الحقيقي: Task Manager ← Memory ← *Available* وإنت شغّال عادي.)
- الموديلات اللي في Task 6 **كلها تدخل بسهولة**:

  | الموديل | الحجم على الـ disk | يدخل في الـ RAM؟ |
  |---|---|---|
  | `qwen2.5:1.5b` | 986 MB | ✅ |
  | `qwen2.5:3b` (عندي) | 1.9 GB | ✅ |
  | `llama3.2:3b` | 2.0 GB | ✅ |
  | `qwen2.5:7b` | 4.7 GB | ✅ (بس أبطأ بشكل واضح، شوف تحت) |

- ⚠️ **الـ "cliff" عندي مختلف عن أجهزة الـ GPU:** على جهاز فيه GPU، المشكلة إن الموديل يعدّي الـ VRAM فيتقسم بين CPU و GPU (offloading) والسرعة تقع. عندي كل حاجة أصلاً في الـ RAM، فالـ cliff بتاعي هو إن **الـ RAM تخلص** والـ Windows يبدأ يستخدم الـ **pagefile على الـ disk**. ساعتها الموديل يبقى بطيء جداً جداً.

### 4. السرعة: الموديل الأكبر = أبطأ بشكل مباشر
- 💡 **قاعدة تقريبية (مش من مصادر الخطوة، هنتأكد منها بالقياس):** على الـ CPU، كل token جديد محتاج يقرا **كل الـ weights** من الـ RAM مرة. فسرعة الـ generation محدودة غالباً بـ **سرعة الـ RAM (memory bandwidth)** أكتر من قوة الـ CPU نفسه.
- يعني الموديل اللي حجمه الضعف هيطلّع tokens/s **قريب من النص**. فالمتوقع إن `qwen2.5:7b` (4.7 GB) يبقى أبطأ من `qwen2.5:3b` (1.9 GB) بحوالي **2–2.5 مرة**.
- ✅ هقيس الـ tokens/s الحقيقي في Task 3، وأقارن بين الموديلات في Task 6.

## لو عايز أسرع (للمعرفة بس، مش مطلوب)
- **موديل أصغر** أو **quantization أصغر**: حجم أقل، فسرعة أعلى، بس ممكن جودة أقل (Task 6 هتقولي الجودة كفاية ولا لأ).
- **GPU منفصل** فيه VRAM (NVIDIA مثلاً): أسرع بكتير، بس فلوس.
- **Cloud** (Ollama cloud أو Claude API): موديلات أكبر من غير hardware، بس الداتا بتخرج من جهازي (Task 7).
